# UUID support proposal

Beside a classical `integer` identifiers (ID) for aggregates we can use universally unique identifiers (UUID). The proposal is not limiting to use either one or another approach. We can combine them.

For this we need Interface hierarchy for ID type of Entity/Aggregate which can be any of UUID versions. The Interfaces should be under `\Domain\Aggregate\UUID` namespace.

At lease should be implemented UUIDv4 and UUIDv7 as most commonly used. The developer should choose which one better suits for his needs.

For dealing with UUIDs use some solid library like `ramsey/uuid`.

The Framework should not push to use UUID for Aggregate IDs. It is optional and up to a developer choice.

## Aggregate example

Aggregate UUID implementation with dual ID type support example. The dual ID where an `id` property is usually a database autogenerated incremental ID which is good for URLs and more user friendly than UUID. The problem with regular integer ID is that a new Entity/Aggregate cannot have an ID before you save it to a database. While with UUID Entities/Aggregates will always have the uuids.
```php
class Post implements AggregateInterface
{
    private AggregateIdInterface $uuid;
    private int $id;
    private string $title = '';

    public function __construct()
    {
        $this->uuid = new UuidV4();
        // ...
    }

    public function getUuid(): AggregateIdInterface
    {
        return $this->uuid;
    }

    /**
     * For restoring Aggregate from persistance layer
     */
    public function setUuid(string $uuid): self
    {
        $this->uuid->setValue($uuid);
        return $this;
    }

    // ... rest of the class implementation
}
```

## Interface hierarchy

```php
interface AggregateIdInterface
{
    public function toString(): string;
    public function equals(AggregateIdInterface $other): bool;
}

interface UuidInterface extends AggregateIdInterface
{
    public function getUuid(): UuidInterface;
}

class PostId implements UuidInterface
{
    private string $value;

    public function __construct(string $uuid = null)
    {
        $this->value = $uuid ?? Uuid::uuid4()->toString();
    }

    // Implementation methods...
}
```

## Considerations

### Mutable UUID
Though UUID are expected to be immutable, we need to hydrate an Aggregate when restoring Aggregate state from a database or from a form presentation. It can be done by reflection, but then the Aggregate looses control on its state. If you fill aggregate properties with reflection the validation and business logic inside `setter` methods are ignored.

### Namespace
Need to decide which namespace is better: `\Domain\Aggregate\UUID` or `\Domain\ValueObject\UUID`. Considering that some ValueObjects can be stored to database, they can have their own UUIDs which will confuse the developers.

## Clarifying questions

- Migration strategy: Are you migrating existing integer IDs to UUIDs, or is this for new aggregates only?
- URL requirements: Do you really need integer IDs in URLs? Could you use slugs instead?
- Database strategy: Will you store both IDs in the same table or use separate tables?
- Framework constraints: What ORM/framework are you using? This affects hydration strategies.
- Performance requirements: Have you benchmarked UUID vs integer performance for your expected load?
- Cross-aggregate references: How will you handle foreign key relationships between aggregates?
- API considerations: Will your APIs expose both ID types or just one?
